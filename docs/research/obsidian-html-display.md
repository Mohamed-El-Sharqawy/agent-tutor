# Research: Displaying generated HTML inside an Obsidian vault

- Date: 2026-08-31
- Question: How can generated HTML content (a dashboard, styled log entries) be displayed from inside an Obsidian vault, and what are the hard constraints?
- Method: primary sources only — the official help vault repo (`obsidianmd/obsidian-help`, which also hosts the official release notes), the first-party API typings (`obsidianmd/obsidian-api`), official obsidian.md blog/changelog pages, and the official GitHub repos of the three named plugins. Note: `docs.obsidian.md` (developer docs) is a client-rendered Obsidian Publish site that could not be scraped; developer-facing facts are cited from `obsidian.d.ts` and release notes instead. The `obsidianmd/obsidian-docs` repo now redirects to `obsidian-help` (verified via the GitHub API).

## Bottom line for agent-tutor

- **`.html` is not a note format.** The official supported list is `.md`, `.base`, `.canvas`, images, audio, video, PDF — no HTML. In-app display of a generated `.html` file requires a community plugin (HTML Reader); that costs the user: Restricted mode off, plugin install, and per-mode security choices (sources: [file formats](https://help.obsidian.md/file-formats), [HTML Reader README](https://github.com/nuthrash/obsidian-html-plugin)).
- **All dashboard data must be baked into the HTML at generation time (Q6 answer).** No supported display path lets client-side JavaScript inside generated HTML read other vault files at runtime: note HTML is sanitized (no `<script>`), HTML Reader blocks scripting in default modes *and* blocks local resource loads, and iframing local vault URLs was removed from Obsidian for security in v1.2.8.
- **`<iframe>` inside a markdown note is officially a web-page embed feature only.** Framing local files is unsupported today (`app://local` removed as an iframe vulnerability, v1.2.8). Do not build the dashboard on a local-file iframe.
- **Custom Frames can only show content served over http(s).** Desktop uses an Electron `<webview>` on a user-supplied URL; framing `app://` vault URLs is undocumented and unverified. If the tutor ever serves the dashboard from a local HTTP server, Custom Frames (or its `custom-frames` markdown code block) becomes viable; otherwise it is irrelevant.
- **The only sanctioned "runtime data" route is Dataview inside markdown, not HTML.** DQL renders live tables from frontmatter with just the plugin installed; DataviewJS can read the vault at runtime but requires the user to enable "Enable JavaScript Queries" (default **off**) and runs as trusted plugin-level code.
- **Recommendation:** keep the current agent-tutor design — markdown notes + inline SVG charts. If an HTML dashboard is ever added, treat it as a static snapshot: fully self-contained, script-free, regenerated by the agent on change (HTML Reader auto-reloads externally modified files), and linkable once "Show all file types" is enabled.
- Styling inside notes is officially done with sanitized inline HTML plus CSS snippets; the sanitizer's exact allowlist is not published, so generated styling must be defensive (inline `style` attributes, no reliance on `<style>` blocks).

## Q1 — Does Obsidian open/render a standalone `.html` file as a note?

**No.** The official list of supported file types is: Markdown `.md`, Bases `.base`, JSON Canvas `.canvas`, images (`.avif .bmp .gif .jpeg .jpg .png .svg .webp`), audio (`.flac .m4a .mp3 .ogg .wav .webm .3gp`), video (`.mkv .mov .mp4 .ogv .webm`), and PDF `.pdf`. The page explicitly says: "You can extend Obsidian to support other file formats using Community plugins." (source: [Accepted file formats](https://help.obsidian.md/file-formats), repo path [`en/Files and folders/Accepted file formats.md`](https://github.com/obsidianmd/obsidian-help/blob/master/en/Files%20and%20folders/Accepted%20file%20formats.md))

Only Markdown notes (and `.canvas`/`.base` via core plugins) open as editable document views; embedded files are limited to "any of the [[Accepted file formats]]" (source: [Embed files](https://help.obsidian.md/embeds)). A `.html` file therefore renders in-app only after installing a viewer plugin such as HTML Reader, which registers itself for `.html`/`.htm` (source: [HTML Reader README](https://github.com/nuthrash/obsidian-html-plugin)).

## Q2 — HTML embedded inside a `.md` note: what is sanitized/allowed?

- **Obsidian sanitizes all HTML in notes.** Official wording: "Allowing HTML inside your notes comes with risks. To prevent malicious code from doing harm, Obsidian _sanitizes_ any HTML in your notes." The page's own example is `<script>`: if HTML were not sanitized, "an attacker could convince you to paste a text containing JavaScript that extracts sensitive information" (source: [HTML content](https://help.obsidian.md/html), repo path [`en/Editing and formatting/HTML content.md`](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/HTML%20content.md)).
- **Scripts never run from note HTML, under any setting.** There is no setting that relaxes note-HTML sanitization; script execution in a vault only happens through plugins (community plugins, or Dataview's JS blocks), which run unsandboxed at app level (sources: [HTML content](https://help.obsidian.md/html); [Plugin security](https://help.obsidian.md/plugin-security)).
- **`<iframe>` is allowed and documented — for web pages.** "To embed a web page, add the following in your note: `<iframe src="INSERT YOUR URL HERE"></iframe>`", with a note that some sites refuse embedding (source: [Embed web pages](https://help.obsidian.md/embed-web-pages)). Release history: iframes allowed since v0.8.1; "HTML `<iframe>` now has a sandbox attribute added for extra security" since v0.9.5; "HTML blocks, including iframes are now rendered" in Live Preview since v0.13.6; links clicked inside iframes open in the default browser (v1.3.2) (sources: [v0.8.1](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.8.1.md), [v0.9.5](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.9.5.md), [v0.13.6](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.13.6.md), [v1.3.2](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v1.3.2.md)).
- **Documented structural limits:** no Markdown inside HTML blocks; HTML blocks must be self-contained with no blank lines, or the block breaks (source: [HTML content](https://help.obsidian.md/html)).
- **`<style>` blocks: not documented either way.** The sanitizer's allowlist is not published; the official styling mechanism for notes is CSS snippets in the config folder (`.obsidian/snippets/`), optionally scoped per-note via the `cssclasses` property (source: [CSS snippets](https://help.obsidian.md/snippets)). Generated HTML should assume `<style>`/`<script>` may be stripped and inline its final styles.
- Since v1.8.2, `<source>` HTML elements support relative links inside markdown notes (source: [v1.8.2 release notes](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v1.8.2.md)) — a narrow allowance for local media in `.md`, not general local-file access for HTML documents.

## Q3 — Can a note iframe a local HTML file from the vault (app:// / capacitor://)?

**Not supported today; historically possible, removed for security.**

- v0.11.0 (2020): "You can now use `file:///` absolute paths to embed images and iframes from your local machine." (source: [v0.11.0 release notes](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.11.0.md))
- v1.2.8 (2022): "Removed support for `app://local` URLs. These were reported as a potential vulnerability when using iframes." The same note tells plugin developers to use `vault.getResourcePath(file)` / `vault.adapter.getResourcePath(vaultPath)` instead — "These also work on mobile." (source: [v1.2.8 release notes](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v1.2.8.md))
- The internal resource-URL scheme is documented only at API level: `Platform.resourcePathPrefix` "returns `file:///` on mobile [and] `app://random-id/` on desktop (Replaces the old format of `app://local/`)"; `Vault.getResourcePath(file)` "Returns a URI for the browser engine to use, for example to embed an image" (source: [`obsidian.d.ts`](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts), `Platform.resourcePathPrefix` and `Vault.getResourcePath` declarations).
- The official embed documentation covers only web pages (iframe) and accepted vault file formats (embed syntax); no documented way exists to point a note's iframe at a vault file (sources: [Embed web pages](https://help.obsidian.md/embed-web-pages), [Embed files](https://help.obsidian.md/embeds)).
- Community corroboration (not official documentation): a 2024 forum thread reports local-HTML iframes that used to work ("plotly graphs") rendering blank after an update ([forum.obsidian.md/t/74509](https://forum.obsidian.md/t/iframe-no-longer-loading-local-html-files/74509)).
- `capacitor://` URLs do not appear in any fetched primary source; the typings say the mobile resource prefix is `file:///` (source: [`obsidian.d.ts`](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts)).

**Clickjacking/sandbox caveats:** note iframes carry a sandbox attribute (v0.9.5, above), and the `app://local` removal (v1.2.8) is the explicit documented case of local-URL framing being treated as a vulnerability. Custom Frames' mobile path uses a heavily sandboxed iframe (see Q4). The Web viewer core plugin — an audited Chromium webview for *external* links — was hardened precisely around WebView pitfalls, per Obsidian's second Cure53 audit (sources: [Web viewer](https://help.obsidian.md/plugins/web-viewer), [Cure53 audit blog post](https://obsidian.md/blog/cure53-second-client-audit/)).

## Q4 — Community plugins: what each enables for a GENERATED dashboard, and the install/config cost

### HTML Reader (`nuthrash/obsidian-html-plugin`)

- What it enables: drop a `.html`/`.htm` file into the vault and "Click any HTML or HTM item to open it" in an Obsidian tab. This is the direct answer to "display a generated dashboard file". (source: [README](https://github.com/nuthrash/obsidian-html-plugin))
- Operating modes (user-picked, security-relevant): **Text**, **High Restricted**, **Balance (default)**, **Low Restricted**, **Unrestricted**. In the default Balance mode: images yes, styles yes, **scripting no**, HTML sanitization on, CSS isolated from the app. Even Unrestricted mode warns that external script files "may not be executable due to Obsidian's limitation", and the author labels it "very dangerous". (source: [README, Operating Mode table](https://github.com/nuthrash/obsidian-html-plugin))
- Hard constraints documented by the plugin author: local images via relative `src` or `file:///` do not load — "This is Obsidian's constraint, it disallow to directly access local files through HTML code"; since Obsidian v1.8+ some relative `src` paths work in Markdown documents, "But it still disallowed to load any local resources for HTML(.html) documents." Also: "Almost all script codes cannot work" — inline `<script>` and external scripts are blocked, event-handler attributes are sanitized out. (source: [README, Known issues](https://github.com/nuthrash/obsidian-html-plugin))
- Useful for agent workflows: **Auto Reload On File Change** (on by default) reloads the view when the file is regenerated externally, preserving scroll; **Form State Persistence** (off by default) can write interactive state back into the HTML file as an inert JSON block. (source: [README](https://github.com/nuthrash/obsidian-html-plugin))
- Cost to the user: turn off Restricted mode, install from Community plugins, enable, optionally pick an operating mode (sources: [README](https://github.com/nuthrash/obsidian-html-plugin); [Plugin security](https://help.obsidian.md/plugin-security)).

### Custom Frames (`Ellpeck/ObsidianCustomFrames`)

- What it enables: "turns web apps into panes using iframes with custom styling"; user-defined frames with any URL, optional per-frame custom CSS and JS, openable as center/side panes, and embeddable inside notes via a `custom-frames` code block that renders "in Live Preview and Reading mode". (source: [README](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/README.md))
- Implementation (source: [`src/frame.ts`](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/src/frame.ts)): on desktop it creates an Electron `<webview>` (unless "force iframe") with `partition = "persist:vault-" + app.appId` and injects the user's custom JS/CSS via `executeJavaScript`/`insertCSS`; otherwise it creates an `<iframe>` with `sandbox="allow-forms allow-modals allow-popups allow-presentation allow-same-origin allow-scripts allow-top-navigation-by-user-activation allow-downloads"`. Frame settings include `url`, `customJs`, `customCss`, `forceIframe`, `hideOnMobile` ([`src/settings.ts`](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/src/settings.ts)).
- For a *generated* dashboard: only viable if the dashboard is served over http(s) (e.g., a local server) — the frame `src` is a URL parsed with `new URL()`. Framing vault-local `app://` URLs is undocumented and unverified. On mobile, iframes are heavily restricted ("a lot of sites won't work there", CORS/cookie limitations; per-frame "Disable on Mobile" exists). (sources: [README](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/README.md), [`src/frame.ts`](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/src/frame.ts))
- Cost: Restricted mode off, install, manually create a custom frame with a URL; popups open in the default browser unless the Web viewer core plugin is enabled (source: [README](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/README.md)).

### Dataview (`blacksmithgu/obsidian-dataview`)

- What it enables: query the vault as a database from inside markdown. Four query modes: DQL code blocks, inline expressions, DataviewJS code blocks, inline JS expressions. A generated dashboard in markdown can embed `dataview` blocks that recompute from note frontmatter on every render. (source: [README](https://github.com/blacksmithgu/obsidian-dataview/blob/master/README.md))
- Security model, in the author's words: "JavaScript queries ... run at the same level of access as any other Obsidian plugin. This means they can potentially rewrite, create, or delete files, as well as make network calls. ... Regular Dataview queries are sandboxed and cannot make negative changes to your vault." (source: [README, JavaScript Queries: Security Note](https://github.com/blacksmithgu/obsidian-dataview/blob/master/README.md))
- Defaults on install: `enableInlineDataview: true` (DQL/inline queries work out of the box), but `enableDataviewJs: false` and `enableInlineDataviewJs: false` — **DataviewJS does not run until the user enables it** (source: [`src/settings.ts`, `DEFAULT_SETTINGS`](https://github.com/blacksmithgu/obsidian-dataview/blob/master/src/settings.ts)).
- Cost: Restricted mode off + install for everything; plus flipping "Enable JavaScript Queries" for the JS route. For an agent-generated dashboard, DQL tables/lists are the zero-extra-toggles option; anything richer needs the JS toggle.

## Q5 — Fallback: linking an `.html` file; indexer, wikilinks, click-through

- By default the vault indexer shows accepted formats only — the File explorer lets you "browse notes and other [[Accepted file formats]]", which excludes `.html` (sources: [File explorer](https://help.obsidian.md/plugins/file-explorer), [Accepted file formats](https://help.obsidian.md/file-formats)).
- The opt-in is **Settings → Files and links → "Show all file types"**: "Show files with any extension even if Obsidian can't open them natively, so you can link to them and see them in File Explorer and Quick Switcher." (source: [Settings](https://help.obsidian.md/settings), repo path [`en/User interface/Settings.md`](https://github.com/obsidianmd/obsidian-help/blob/master/en/User%20interface/Settings.md)) — this is what makes a generated `Dashboard.html` visible, searchable in Quick Switcher, and linkable.
- Wikilinking rules: "you can link to any of the [[Accepted file formats]]; links to file formats other than Markdown need to include a file extension, such as `[[Figure 1.png]]`" (source: [Internal links](https://help.obsidian.md/links)). With "Show all file types" on, the extension-carrying wikilink `[[Dashboard.html]]` is the documented way to reference it.
- Click-through experience: **officially undocumented for non-openable files without a viewer plugin** (the Settings blurb only promises visibility and linkability). With HTML Reader installed, clicking an HTML item opens the in-app reader (source: [HTML Reader README](https://github.com/nuthrash/obsidian-html-plugin)). "Excluded files" patterns deprioritize files in link suggestions (source: [Internal links](https://help.obsidian.md/links)).
- Practical fallback the agent can rely on without any plugin: generate the file, enable "Show all file types", and link it — but expect the actual "open in external browser" step to be the OS-level behavior, which Obsidian's help does not formally document for `.html`.

## Q6 — Can client-side JS in the embedded/iframe page read OTHER vault files at runtime?

**No — under every supported display path, the page cannot read other vault files. All data must be baked into the HTML at generation time.** Path by path:

1. **HTML embedded in a markdown note:** Obsidian sanitizes note HTML; `<script>` never executes, so there is no JS to fetch anything (source: [HTML content](https://help.obsidian.md/html)).
2. **Generated `.html` opened via HTML Reader:** scripting is off in the default Balance mode, sanitization strips event handlers, and — decisive even in permissive modes — "Obsidian's constraint" blocks local file access from HTML documents: relative `src`, `file:///`, and local resources are not loaded for `.html` files (source: [HTML Reader README, Known issues](https://github.com/nuthrash/obsidian-html-plugin)). There is no bridge from the rendered page to the Obsidian Vault API.
3. **Iframing the vault file from a note:** the only documented local-URL mechanisms were `file:///` embeds (v0.11.0) and `app://local` URLs, and the latter was **removed in v1.2.8 because it was "reported as a potential vulnerability when using iframes"** — i.e., Obsidian deliberately closed the door on framed pages touching local resources (sources: [v0.11.0](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.11.0.md), [v1.2.8](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v1.2.8.md)). Note iframes also carry a sandbox attribute since v0.9.5 ([v0.9.5](https://github.com/obsidianmd/obsidian-help/blob/master/Release%20notes/v0.9.5.md)).
4. **Custom Frames / Web viewer (webview-based):** these load arbitrary *web* content; nothing in their docs or source grants framed content access to vault files, and the mobile iframe is explicitly sandboxed (sources: [Custom Frames README](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/README.md), [`src/frame.ts`](https://github.com/Ellpeck/ObsidianCustomFrames/blob/master/src/frame.ts), [Web viewer](https://help.obsidian.md/plugins/web-viewer)). Obsidian's security model is blunt: *plugins* "can access files on your computer" and "are not sandboxed", while web content is contained (sources: [Plugin security](https://help.obsidian.md/plugin-security), [Web viewer security section](https://help.obsidian.md/plugins/web-viewer)).
5. **The sanctioned runtime readers of vault data live at plugin level:** community plugins (full file access) and DataviewJS blocks, which "run at the same level of access as any other Obsidian plugin" — but DataviewJS ships disabled by default (sources: [Plugin security](https://help.obsidian.md/plugin-security); [Dataview README](https://github.com/blacksmithgu/obsidian-dataview/blob/master/README.md); [Dataview `src/settings.ts`](https://github.com/blacksmithgu/obsidian-dataview/blob/master/src/settings.ts)).

**Consequences for the tutor pipeline:** a generated HTML dashboard is a *snapshot*. To "refresh" it, the agent regenerates the file (HTML Reader's auto-reload makes this seamless in-app). If genuinely live data is required at render time, the correct artifact is not HTML but a markdown note containing Dataview (DQL, or DataviewJS where the user opted in) — or a small companion plugin. Fetch-based designs (page JS pulling `app://` markdown at runtime) contradict the documented security posture and must not be used.

## Where primary sources were inconclusive

- **Sanitizer allowlist:** Obsidian documents *that* it sanitizes note HTML but publishes no per-tag allow/deny list; `<style>` handling in notes is unspecified (only CSS snippets are documented as the styling mechanism).
- **Click behavior for linked non-openable files** (e.g., `.html` with no viewer plugin): the Settings page promises visibility/linkability only; the actual default open action is not formally documented.
- **Custom Frames loading `app://` URLs:** undocumented in the plugin; unverified behavior (would require testing against Electron's custom-protocol handling).
- **Current status of v0.11.0's `file:///` iframe embeds:** no official statement that they were removed; community reports (2024 forum thread) indicate local-file iframes broke at some point. Treat as unsupported.
- **Mobile `capacitor://` specifics:** absent from the fetched primary sources; `obsidian.d.ts` only says the mobile resource prefix is `file:///`.
- **docs.obsidian.md pages** (e.g., `getResourcePath`) exist but render client-side, so their prose could not be quoted; the equivalent API facts were cited from `obsidian.d.ts` instead.
